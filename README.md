# Функциональные требования

## 1. Архитектура приложения

- Приложение должно работать как **Single Page Application (SPA)**.
- Переключение между страницами (**Главная**, **Детали монеты**, **Портфель**) должно происходить **без перезагрузки**.

## 2. Главная страница

### 2.1. Таблица криптовалют

- Динамическая таблица с **топ-100 криптовалют**.
- Поля таблицы:
  - ранг;
  - название;
  - текущая цена;
  - изменение за 24 часа (зелёный/красный цвет текста);
  - капитализация.
- Если каких-то данных в API нет — эти данные **не отображать**.

### 2.2. Поиск, фильтрация и сортировка

- Панель с поиском и фильтрацией:
  - поиск по названию;
  - фильтрация по диапазону цен;
  - сортировка по клику на заголовки столбцов (вверх/вниз).
- Всё это должно происходить **без перезагрузки страницы**.

### 2.3. Интерактивные виджеты

- **3–4 карточки** сверху таблицы с глобальными метриками рынка:
  - общая капитализация;
  - изменение за сутки;
  - и другие (на выбор разработчика).

## 3. Страница деталей монеты

- Должна открываться по **динамическому URL** (например, `#coin?id=bitcoin` или `/coin/bitcoin`).
- Содержит:
  - исторический график с отображением изменения цены монеты;
  - переключатель таймфреймов (**1 день, 7 дней, 30 дней, 1 год**);
  - быстрый пересчёт (конвертер) в **USD/EUR/BTC**.

## 4. Страница инвестиционного портфеля

### 4.1. Форма добавления транзакций

- Пользователь выбирает монету, вводит количество и цену покупки.

### 4.2. Отображение портфеля

- Структура портфеля в виде **круговой диаграммы (Pie Chart)** в процентном соотношении.
- Расчёт **текущей стоимости портфеля** и **общей прибыли/убытка (PnL)** на основе актуальных цен из API.

### 4.3. Сохранение данных

- Все данные портфеля сохраняются в **localStorage**.

## 5. Синхронизация между вкладками

- Если приложение открыто в двух вкладках браузера, добавление транзакции в портфель в одной вкладке должно **мгновенно обновлять данные во второй вкладке** без ручной перезагрузки.
- Реализовать через **StorageEvent** или **BroadcastChannel API**.

## 6. Оптимизация поиска

- Написать **свою функцию debounce** для поисковой строки.
- Запросы к API и фильтрация массива не должны срабатывать на каждое нажатие клавиши (**задержка 300 мс**).

## 7. Автообновление данных (Polling)

- Периодический фоновый опрос API **каждые 30–60 секунд** с помощью `setInterval`.
- При обновлении данных должен отображаться **индикатор обновления (Spinner/Progress bar)**.
- Таблица должна **плавно обновляться**, не сбрасывая текущий скролл пользователя.

## 8. Обработка ошибок и Rate Limits

- Бесплатные API имеют жёсткие лимиты на количество запросов в минуту (**Rate Limits**).
- Приложение должно корректно обрабатывать:
  - ошибку **429 Too Many Requests**;
  - сетевые сбои.
- Приостановка работы API **не должна приводить к падению приложения**.
- Пользователю показывается **кастомное модальное окно** или уведомление об ошибке.

## 9. Производительность

- При частом обновлении данных (например, при поиске) **запрещено** делать полную замену `document.body.innerHTML = ...`, так как это сильно бьёт по производительности.

## 10. Безопасность (XSS)

- Реализовать защиту от **XSS-атак**.
- При вставке строк (названий монет, полученных из API) использовать безопасный `textContent` или `innerText` вместо `innerHTML`.
